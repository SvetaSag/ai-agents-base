# Занятие 3 — несколько агентов: A2A и Langfuse

Берём агента-аналитика банка из занятия 2 и добавляем второго агента —
**риск-менеджера**. Риск-менеджер решает, можно ли выдать кредит, но доступа
к базе у него нет: все факты он спрашивает у аналитика по протоколу **A2A**.
Затем подключаем **Langfuse** и видим каждый шаг обоих агентов одним деревом.

```
вопрос → ⚖️ риск-менеджер ──A2A──▶ 📊 аналитик ──MCP──▶ 🔧 mcp_server.py ──▶ Postgres «bank»
               │                        │
               └────────── трейсы ──────┴──────────▶ Langfuse (http://localhost:3000)
```

| Агент | Что умеет | Что знает |
|---|---|---|
| 📊 аналитик (`analyst_agent.py`) | ходит в базу через MCP, пишет SQL | данные банка |
| ⚖️ риск-менеджер (`risk_agent.py`, блокнот 02) | решает по кредиту, считает платёж, **помнит разговор** | кредитную политику; доступа к базе нет |

## Подготовка

```bash
cp .env.example .env                    # вписать OPENROUTER_API_KEY (и при желании MODEL)
uv sync
docker compose up -d                    # база банка (:5435) + Langfuse (:3000); первый раз качает образы
uv run python scripts/load_berka.py     # ~30 с: датасет банка (тот же, что в занятии 2)
```

Langfuse при первом старте сам создаёт проект и ключи, которые уже вписаны в
`.env.example`. Вход в интерфейс: http://localhost:3000, логин `admin@example.com`,
пароль `lesson3-admin`. Стек Langfuse состоит из шести контейнеров и занимает
около 2–3 ГБ памяти. Если ноутбук не тянет, можно взять бесплатный
[Langfuse Cloud](https://cloud.langfuse.com) и вписать в `.env` его адрес и ключи.

## Во время занятия: два терминала + блокноты

```bash
uv run python mcp_server.py        # терминал 1: MCP-сервер с инструментами → http://localhost:8101/mcp
uv run python analyst_agent.py     # терминал 2: аналитик как A2A-агент     → http://localhost:8102
uv run jupyter lab                 # блокноты
```

В терминале 1 видно каждый вызов инструмента и SQL. В терминале 2 — каждый
вопрос, пришедший аналитику, и его ответ. Каждый блокнот в начале проверяет,
что оба сервера запущены.

## Этапы

### Часть 1 — A2A на пальцах · `01_a2a_basics.ipynb`

| | MCP | A2A |
|---|---|---|
| кто с кем | агент ↔ инструмент | агент ↔ агент |
| что видно снаружи | инструменты и их аргументы | только карточка и ответ |
| возможности | `tools/list` | карточка `/.well-known/agent-card.json` |
| единица работы | вызов инструмента | задача (Task) со статусами |

1. карточка аналитика: имя, описание, навыки, адрес;
2. сообщение «руками»: JSON-RPC `SendMessage` через `httpx`, в ответ приходит задача со статусом и артефактом;
3. то же через клиент `a2a-sdk`;
4. как аналитик стал A2A-агентом: карточка + граф из занятия 2 + обёртка `AgentExecutor`.

### Часть 2 — второй агент · `02_two_agents.ipynb`

1. `ask_analyst` — инструмент, внутри которого A2A-запрос к аналитику;
2. `loan_payment` — обычный инструмент (аннуитетный платёж);
3. риск-менеджер: `create_agent` + кредитная политика в промпте;
4. три клиента: **2378 — одобрить**, **1583 — отказать** (просроченный кредит),
   **1 — отказать** (платёж больше 30 % прихода).

Риск-менеджер сам решает, какие вопросы задать аналитику, и часто задаёт
несколько сразу.

**Память.** Помнит разговор тот, кто общается с человеком: у риск-менеджера
есть checkpointer, и на уточнение «а если 300 000?» он помнит клиента.
Аналитик — исполнитель **без памяти**: получает самодостаточные вопросы.
Общий у агентов только **номер сессии** (в `metadata` A2A-сообщения), и он
нужен для журнала в Langfuse, а не для памяти. Почему не один номер памяти
на всех: параллельные вопросы перемешали бы историю, а разговоры разных
агентов-заказчиков слились бы в один.

### Часть 3 — Langfuse · `03_langfuse.ipynb`

1. трейс = корневой span (`start_as_current_observation`) + `CallbackHandler` в конфиге графа;
2. что видно: дерево шагов, у каждого вызова LLM — промпт, ответ, токены, время, стоимость;
3. дерево трейса прямо в блокноте (`trace_view.py`);
4. сессии (`session_id`: оба агента в одной сессии) и оценки (`create_score`);
5. проблема: работа аналитика попала в **отдельные** трейсы.

### Часть 4 — один трейс на двух агентов · `04_trace_a2a.ipynb`

1. риск-менеджер кладёт в `metadata` A2A-сообщения `trace_id` и номер своего шага;
2. аналитик продолжает **чужой** трейс: `caller_span(...)` в `analyst_agent.py` делает шаг риск-менеджера родителем своих шагов;
3. результат — одно дерево: риск-менеджер → A2A → аналитик → MCP-инструменты.
   Видно, где тратится время и сколько токенов потратил каждый агент.

## Файлы

```
mcp_server.py          MCP-сервер: list_tables, describe_table, run_sql (HTTP :8101)
analyst_agent.py       аналитик: граф LangGraph + A2A-сервер (:8102) + трейсы в Langfuse
risk_agent.py          риск-менеджер (тот же, что в блокноте 02) — для блокнотов 03–04
trace_view.py          печать трейса Langfuse деревом
01–04_*.ipynb          блокноты частей 1–4
docker-compose.yml     база банка + self-hosted Langfuse
scripts/load_berka.py  загрузка датасета
db/init.sql            роль mcp_reader только для чтения
```

Порты: база 5435, MCP 8101, аналитик 8102, Langfuse 3000 и 9090. Они не
пересекаются с занятием 2, поэтому оба занятия можно держать запущенными
одновременно.
