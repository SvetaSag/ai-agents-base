# Занятие 2 — интеграции: MCP, веб-чат и Telegram

Строим **агента-аналитика банка**. Он отвечает на вопросы по реальным данным
чешского банка (датасет Berka: ~1 млн транзакций, 4 500 счетов, 5 369 клиентов,
682 кредита, 1993–1998, суммы в кронах). Данные лежат в Postgres, а агент
добирается до них через **MCP-сервер**, который мы пишем сами.

Занятие идёт этапами: от игрушечного MCP-сервера в блокноте до сервиса в
докере с веб-чатом и Telegram-ботом, у которых общие сессии.

```
 0  MCP на пальцах         игрушечный сервер + клиент в одном блокноте
 1  сервер для базы        свой MCP-сервер поверх Postgres, клиент вызывает его руками
 2  LLM + LangGraph        модель сама вызывает инструменты сервера
 3  авторизация           HTTP-сервер пускает только клиентов с токеном
 4  готовые серверы       fetch и DeepWiki рядом с нашим
 5  сервис в докере       API + веб-чат, память и сессии в Postgres
 6  Telegram-бот          те же сессии из Telegram
```

## Подготовка

```bash
cp .env.example .env                    # вписать OPENROUTER_API_KEY (и при желании MODEL)
uv sync
docker compose up -d postgres           # Postgres на порту 5434
uv run python scripts/load_berka.py     # ~30 с: скачивает датасет в data/ и грузит в базу
uv run jupyter lab                      # или открыть папку в VS Code / Cursor, ядро — .venv
```

| Этап | База | Ключ LLM | Ещё |
|------|:----:|:--------:|-----|
| 0 | — | — | — |
| 1 | ✓ | — | — |
| 2–3 | ✓ | ✓ | — |
| 4 | ✓ | ✓ | интернет, `uvx` (ставится вместе с `uv`) |
| 5 | в докере | ✓ | Docker |
| 6 | в докере | ✓ | `TELEGRAM_BOT_TOKEN` |

**О данных.** Датасет скачивается с публичного сервера ЧВУТ
(`relational.fel.cvut.cz`). Таблицы и колонки переведены на английский, у
каждой есть описание (`COMMENT`), по нему агент разбирается в базе.
Повторный запуск загрузчика ничего не делает, `--force` перезагружает данные
из кэша `data/`.

**Права.** MCP-сервер ходит в базу ролью `mcp_reader`, которой разрешено
только читать (`db/init.sql`). Даже если модель напишет `DELETE`, база его
не выполнит.

## Этап 0 — MCP на пальцах · `00_mcp_hello.ipynb`

Сервер и клиент в одном блокноте, без базы и докера.

- сервер — обычные функции с `@mcp.tool()`, `@mcp.resource()`, `@mcp.prompt()`; протокол берёт на себя FastMCP;
- что видит модель: имя, docstring и JSON-схема аргументов, а не код функции;
- «прослушка провода»: каждое сообщение клиент ⇄ сервер (`initialize` → `tools/list` → `tools/call`);
- ошибка — это обычный ответ с `isError: true`, сервер не падает;
- тот же сервер отдельной программой (`hello_server.py`, транспорт stdio).

## Этап 1 — свой сервер для базы · `01_mcp_server_client.ipynb`

Блокнот записывает сервер в файл `db_server.py`. В нём три инструмента:
`list_tables`, `describe_table`, `run_sql`.

1. клиент запускает сервер сам и подключается к нему (`stdio_client` → `ClientSession` → `initialize`);
2. вызываем инструменты руками: таблицы → колонки → SQL;
3. `DELETE` не проходит, потому что роль в базе может только читать;
4. тот же сервер как сетевой сервис: `python db_server.py --http` → клиент подключается по адресу `http://localhost:8011/mcp`.

| | stdio | HTTP |
|---|---|---|
| кто запускает сервер | клиент, как подпроцесс | сервер запущен заранее |
| конфиг клиента | команда | адрес |
| когда | локальные инструменты | общий сервис, докер, много клиентов |

## Этап 2 — LLM в LangGraph · `02_mcp_langgraph.ipynb`

Теперь инструменты вызывает модель.

1. `MultiServerMCPClient` → `get_tools()`: инструменты сервера становятся обычными LangChain-инструментами;
2. граф из занятия 1: `agent` (модель) ⇄ `tools` (`ToolNode`), память — `InMemorySaver`;
3. `ask()` печатает каждый шаг: 🤖 что модель вызвала, 🔧 что ответил сервер, 💬 ответ.

Модель сама смотрит таблицы, пишет SQL и помнит предыдущие вопросы. SQL
выводится на экран, чтобы его можно было проверить: агент может ошибиться.

## Этап 3 — авторизация · `03_mcp_auth.ipynb`

stdio защищать не нужно. HTTP-сервер нужно: к нему может обратиться любой,
кто знает адрес. Блокнот пишет `secure_server.py` с теми же инструментами и
проверкой токена.

- сервер: `TokenVerifier` сверяет `Authorization: Bearer <токен>` с секретом из переменной окружения;
- без токена и с неверным токеном сервер отвечает **401**;
- клиент передаёт токен через `headers` в конфиге `MultiServerMCPClient`, а агент получает уже готовые инструменты;
- в проде нужны ещё HTTPS и отдельный токен на каждого клиента; для публичных серверов используют OAuth 2.1.

## Этап 4 — готовые MCP-серверы · `04_ready_mcp.ipynb`

- **fetch** (официальный, локально через `uvx`) скачивает страницу: берём курс валют ЧНБ;
- **DeepWiki** (удалённый, по HTTP) отвечает на вопросы о GitHub-репозиториях;
- один агент работает сразу с тремя серверами: `bank` + `fetch` + `deepwiki`.

Чужой сервер — это чужой код, а то, что он вернул, — недоверенные данные.
Берите серверы из проверенных источников.

Блокноты 03 и 04 используют `db_server.py`, поэтому сначала выполните 01.

## Этап 5 — сервис в докере

```bash
docker compose up -d --build
```

Откройте **http://localhost:8080** — это веб-чат. Слева список сессий, справа
разговор. Над каждым ответом — какие инструменты вызвал агент (SQL внутри,
по клику).

```
 браузер ──┐                                     ┌─▶ MCP-сервер ─▶ Postgres «bank» (только чтение)
           ├─▶ API (FastAPI) ─▶ LangGraph-агент ─┤
 Telegram ─┘        │                            └─▶ OpenRouter (LLM)
                    └─▶ Postgres «agent»: сессии + память агента
```

| Сервис | Порт | Что делает |
|--------|------|------------|
| `postgres` | 5434 | базы `bank` (данные) и `agent` (сессии, память) |
| `seed` | — | один раз загружает датасет и завершается |
| `mcp` | 8001 | MCP-сервер по HTTP: `http://localhost:8001/mcp` |
| `api` | 8080 | агент + API + веб-чат |
| `bot` | — | Telegram-бот (этап 6) |

Что изменилось по сравнению с блокнотами:

- **сервер** — `bank_mcp/server.py`, доработанная версия `db_server.py`.
  У `run_sql` три слоя защиты: права роли, парсер «ровно один `SELECT`»
  (`sqlglot`), транзакция только на чтение с таймаутом 15 с и лимитом строк.
  Добавлены инструмент `account_summary`, ресурс со схемой базы и промпт.
- **память** — `AsyncPostgresSaver` вместо `InMemorySaver`: разговоры
  сохраняются после перезапуска. Номер сессии — это `thread_id` графа.
- **один API для всех клиентов** — `app/api.py`. Веб-страница и бот ходят в
  одни и те же эндпоинты.

Код сервиса — три файла:

| файл | что внутри |
|---|---|
| `app/agent.py` | граф из блокнота 02 + `chat()` (вопрос → ответ) и `history()` (переписка сессии) |
| `app/api.py` | FastAPI: при старте подключается к MCP и Postgres; таблица `sessions`; 6 эндпоинтов |
| `app/static/index.html` | страница: список сессий, переписка, поле ввода (обычный JS, без сборки) |

| Эндпоинт | Что делает |
|---|---|
| `GET /api/sessions` | список сессий |
| `POST /api/sessions` | новая сессия (`{"source": "web"}` или `"telegram"`) |
| `GET /api/sessions/{id}` | одна сессия |
| `GET /api/sessions/{id}/messages` | её переписка — из памяти агента |
| `POST /api/sessions/{id}/chat` | отправить сообщение, получить ответ |

Логи: `docker compose logs -f api mcp`. В логах `mcp` видно каждый вызов инструмента.
Сервер из докера можно посмотреть в MCP Inspector:
`npx @modelcontextprotocol/inspector` → Streamable HTTP → `http://localhost:8001/mcp`.

## Этап 6 — Telegram-бот

1. Создайте бота у [@BotFather](https://t.me/BotFather) и впишите токен в `.env` (`TELEGRAM_BOT_TOKEN`).
   Свой user id (его можно узнать у [@userinfobot](https://t.me/userinfobot)) впишите в
   `TELEGRAM_ALLOWED_USERS`, иначе бот будет отвечать всем.
2. `docker compose --profile telegram up -d --build`

| Команда | Что делает |
|---------|------------|
| любой текст | вопрос агенту; в конце ответа — `— сессия #N` |
| `/new` | новая сессия |
| `/continue N` | продолжить сессию N, начатую в Telegram **или в веб-чате** |

**Общие сессии.** Бот не ходит в базу и не вызывает агента напрямую: он
такой же клиент API, как веб-страница. Поэтому:

- пообщались в вебе → в Telegram `/continue N` (номер есть в шапке веб-чата) → агент помнит разговор;
- пообщались в Telegram → сессия появляется в веб-чате (список обновляется раз в 4 с) с пометкой ✈️,
  номер — в конце каждого ответа бота.

Список сессий — в таблице `sessions`, сами сообщения — в памяти агента
(`thread_id` = номер сессии). Какой Telegram-чат на какой сессии, бот помнит
у себя в памяти: после перезапуска бота просто снова `/continue N`.

## Тесты

```bash
uv run pytest -q
```

Тесты используют настоящие Postgres и MCP-сервер, а вместо LLM — простую
заглушку, поэтому токены не тратятся. Проверяется вызов MCP на
реальных данных, память, продолжение одной сессии из веба в Telegram и
обратно, бот (без Telegram: сообщения подаются прямо в диспетчер aiogram) и
атаки на `run_sql` (`tests/test_sql_guard.py`). Нужен запущенный `postgres`
с данными; тесты работают в отдельной базе `agent_test`.
